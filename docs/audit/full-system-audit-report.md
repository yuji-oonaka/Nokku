# 🛰️ NOKKU 統合監査サマリー：真実の同期と地雷撤去

## 1. 🏗️ バックエンド：堅牢な「憲法」の確立

バックエンドは「決済・数量・在庫」の全領域において、**原子性（All or Nothing）**が確保された極めて健全な状態です。

* **在庫管理の鉄則**: チケットの `remaining_count` およびグッズの `stock` は、注文作成（`pending`）時に `lockForUpdate` で先行確保され、キャンセル時に自動復元されるサイクルが確立されました。
* **ポイント経済の安全性**: `PointService` を通じた残高更新と `PointTransaction` への `balance_after`（取引後残高）の記録により、1円単位の監査が可能です。
* **決済の二重処理防止**: Stripe Webhook 側での悲観的ロックとステータスチェックにより、二重発券や二重減算のリスクは排除されています。

---

## 2. 📱 フロントエンド：表示の整合性と「GateScanner」の適正化

「バックエンドの真実を正しく映す」ための検証を行い、現場の違和感を解消しました。

* **【解決済み】GateScannerScreen の専用機化**:
* 据置ゲートにおいて「グッズ引換タブ」を非表示にし、チケット専用モードに固定。
* これにより、入場ゲートでの誤操作リスクを物理的に排除しました。


* **【検証済み】在庫・購入制限の同期**:
* `TicketPurchaseList.tsx` および `ProductDetailScreen.tsx` は、正確に `remaining_count` や `stock` を参照し、完売表示や数量制限を正しく行っています。



---

## 3. 🚩 未解決の「表示の嘘」と今後の課題 (Phase 1)

ロジックは正しいものの、UI側で「古い情報」や「ハードコード」が残っている箇所です。これらを直すことが次のステップとなります。

* **サブスク情報の乖離**: `SubscriptionScreen.tsx` がバックエンド（Stripe）のメタデータではなく、静的な定義ファイルを参照している。
* **チャットの価格・制限の固定化**: 消費ポイントや連投制限秒数がフロントエンドに直接書かれており、バックエンドの設定変更に追従できない。
* **引換情報の解禁（Phase 1 への布石）**:
* `useGateScanner.ts` でグッズ引換時に詳細（商品名・数）が表示されていない。
* バックエンドは既に詳細データを返却しているため、これを表示するだけで「スタッフ補助型・誤渡し防止モード」が実現可能です。
