### 🔍 NOKKU 数量・在庫ロジック 精密監査報告

#### 1. グッズ（商品）在庫のライフサイクル

グッズに関しては、比較的シンプルかつ一貫した設計になっています。

* **定義**: `products.stock` は `unsignedInteger` であり、0未満にならないようDBレベルで保護されています。
* **モデルの挙動**: `Product.php` には在庫を自動操作するマジックメソッド（bootedなど）は存在せず、明示的な命令（`decrement`, `increment`）にのみ従います。
* **注文明細**: `order_items` テーブルは、商品が削除されても注文履歴が壊れないよう、`product_name` と `price_at_purchase` をコピーして保持する堅牢な設計です。
* **リスク点**: 商品が削除（物理削除）されると `order_items.product_id` が `null` になるため、その後に「期限切れキャンセル」が発生しても、在庫を戻す対象（Productレコード）が消失しており、在庫復元が失敗します。

#### 2. チケット・イベントのライフサイクル

チケット周りには、前述の「ねじれ」以外にも、構造的な注意点が見つかりました。

* **イベント全体の制約**: `Event.php` 自体には合計定員をバリデーションするロジックはなく、あくまで `TicketType`（券種）ごとの `capacity` に依存しています。
* **整合性の乖離**:
* `OrderController` は **`remaining_count`** を減らす。
* `TicketService` は **`capacity`** を減らす。
* `CancelExpiredOrders` はチケットに対して **何も戻さない**。


* **結論**: チケット在庫は「減る一方」であり、かつ「減らす場所」もマスタ（定員）と在庫で混在している、極めて不安定な状態です。

#### 3. データベース層の自動化（Trigger等）

* **結果**: マイグレーションファイルを確認しましたが、`AFTER INSERT` や `AFTER UPDATE` といった **DBレベルのトリガー（自動計算）は一切仕込まれていません**。
* **意味**: 数量の不整合は、100% PHP側のロジック（`OrderController`, `TicketService`, `CancelExpiredOrders`）の記述ミスに起因していることが確定しました。

### 🛡️ テックリードの最終診断

「本当にこれだけか？」という問いに対する答えは **「はい、これで全てです」** です。

1. **DB制約**: トリガーなし。Cascade削除のみ。
2. **モデルロジック**: `OrderItem` での「商品・チケット」の排他チェックのみ。
3. **サービスロジック**: `TicketService` の `capacity` 減算のみが異常。
4. **クロップ（Cron）**: `CancelExpiredOrders` のチケット在庫戻し漏れのみが異常。
