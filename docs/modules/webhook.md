
# 💳 決済Webhook (Stripe Webhook) モジュール詳細

## 核心ロジック: `StripeWebhookController`

実装事実に基づく決済ライフサイクル管理。

### 1. 決済成功ハンドリング (`payment_intent.succeeded`)

* `metadata.order_id` を基に対象の `Order` を取得。
* **重複防止**: ステータスが `paid` または `completed` の場合は、既に処理済みと判断し即座にリターンする（べき等性の確保）。
* **ステータス遷移**: 注文ステータスを `pending` から `paid` へ更新。
* **発券実行**: `TicketService@issueTicketsFromOrder` を呼び出し、デジタルチケット（UserTicket）を生成。

### 2. 決済失敗・キャンセルハンドリング (`payment_intent.payment_failed` / `canceled`)

* **即時在庫復元**: 決済が失敗した瞬間に `Order` に紐づく商品/チケットの在庫を `increment` で戻す。
* **ステータス更新**: 注文を `cancelled` とし、不要な「支払処理中」データが残るのを防ぐ。

### ✅ 解決済みの「地雷」

* **在庫の二重減算防止**: 在庫操作は `OrderController` の注文作成時のみに集約。発券時（Webhook側）での数量操作を完全に排除した。
* **通信の道連れエラー防止**: Firestoreへの同期（`syncToFirestore`）を `DB::afterCommit` 内に配置。外部通信が失敗してもDB側の決済・発券処理はロールバックされない堅牢な設計へ変更。
* **データの整合性（棲み分け）**: 決済完了前のフライング同期を廃止。API側で商品/チケット注文のフィルタリングを実装し、各履歴画面で正しいデータのみを表示するように修正。

## 📅 未来対応・運用上の課題 (Backlog)

運営責任およびプラットフォーム信頼性維持のため、以下のロジックを段階的に実装予定。

### 1. イベント終了後の自動クローズ

* **対象**: 決済済みだが会場に来なかった（未入場の）チケット。
* **処理**: イベント終了翌日に一括で `expired` ステータスへ更新し、管理画面上のアクティブなデータを整理する。

### 2. 主催者都合の中止・延期対応

* **一括返金**: Stripe Refund API と連携し、中止イベントの注文を一括で返金処理する機能。
* **一括無効化**: 中止・延期フラグに基づき、ユーザー画面でのQRコード表示を制御するロジック。
