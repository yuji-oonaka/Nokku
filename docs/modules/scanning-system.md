# 🔍 スキャン・入場システム (Scanning System) モジュール詳細

## 核心ロジック: ``TicketAdmissionService``, ``OrderScanController``に基づく実装事実。

### 1. QRコードの自動判別ロジック
* **フォールバック機能:** チケットスキャン時にチケットが見つからない場合、自動的に ``Order`` テーブルを検索する。グッズ引換用QRを誤ってチケットスキャナーで読み込んだ場合、適切なエラー（「グッズ引換モードにしてください」）を返却する親切設計となっている [cite: 25]。

### 2. 厳格な認可プロトコル (RBAC)
* **スタッフ所属チェック:** ``scannerUser->role`` が ``staff`` の場合、そのスタッフの雇用主（``employer_id``）が、イベントの主催アーティスト（``artist_id``）と一致しているかを厳密に検証する [cite: 25]。
* **二重入場・引換の防止:** ``lockForUpdate`` による悲観的ロックを実行。DB更新（``USED`` または ``completed``）後に初めてレスポンスを返すことで、同一QRによる同時入場を物理的に防ぐ [cite: 25]。

### 3. ハイブリッド同期 (MySQL & Firestore)
* **Firestore同期義務:** MySQLの更新に成功した後、必ず ``syncToFirestore`` を呼び出す。チケットなら ``ticket_status``、グッズなら ``order_status`` コレクションへ、スキャナーID付きで即座に反映させる [cite: 25, 26]。

### 🚩 【最重要】実装上の「ねじれ」と地雷
* **在庫減算の不整合:**
    * ``OrderController.php``（注文時）: **``remaining_count``**（残り在庫）を減算 [cite: 20]。
    * ``TicketService.php``（発券時）: **``capacity``**（定員）を減算 。
* **リスク:** 現在の仕様では、チケットが売れるたびに「イベントの定員」そのものが削られてしまう。定員変更ロジックが ``capacity`` を参照しているため、販売が進むほどマスタデータが破壊される。
